## 2. New findings this re-audit (not in prior audit)
### 2a. `_site/` is NOT a duplicate — correction to AUDIT_2026-08-18.md
**The Aug-18 audit claimed `_site/` is a full mirror of the repo root. That is WRONG.**

Verification (this re-audit): `_site/` contains a DIFFERENT file set — it has no `bot.py`, `state.json`,
`images/output.jpg`, `forwilma/`, or `archive/` (root). It holds the GitHub Pages build output:
`index.html`, `style.css`, `app.js`, `_headers` (CSP config), `gallery.json` (301 entries),
`dashboard_data.json` (main 1465 posts / Wilma 16 days), `agents.json`, plus the deployed `carousel/`
slides and `reels/`. Root holds the code, config, and working state. The two dirs share NAME only
(e.g. both have `archive/`, `audio/`, `carousel/`) but the CONTENTS differ.

`_site/` IS NEEDED — `pages_deploy.yml` generates `dashboard_data.json`, `gallery.json`, and
`agents.json` into `_site/`, uploads `_site/` as the GitHub Pages artifact, and deploys it. It must
not be deleted or redirected to a separate `dist/`. The "duplicate" appearance came from a naive
`ls` comparison that matched by filename; the actual file BLOBS differ.

| bot.py | 1282 | OCR.space image parse |
| bot.py | 2707 | API call (context unknown) |
| scripts/brand_guardian.py | 200 | leak-floor LLM judge POST |
| scripts/openrouter_captions.py | 161, 309 | caption tailoring POST |
| scripts/prepare_assets.py | 20 | quote bundle POST |
| scripts/publish.py | 86 | caption POST |
| scripts/delete_bundle_322.py | 56,74,145,243,261 | deletion calls |
- No `timeout=` anywhere on 20+ request call sites. CI can hang indefinitely on a dead runner.
- Risk: master_content_gen/wilma_gen/main publisher all wait on these; a dead network = workflow
  timeout without a visible error.
- Recommend: every requests.* call site adds `timeout=(3, 30)` (connect 3s, read 30s).

  workspace. No code collision, but the root-level `agents.json`/`agent_orchestrator.py` and the
  Hermes `agents/` dir are unrelated and must not be conflated.

## 3. Reels tracking — memory-savings analysis (the pending item)
### What the pipeline does now
- generate_reel.py --template hook_blast|cinematic_quote|word_ripple generates a 9s reel from
  master_reflection or the bundle's instagram caption.
- Two competing counters exist: bot.py writes reel_rotation.json (per-post rotation) and the
  workflow's inline script uses post_id % 3 (independent). Same effect, different sources, no
  single source of truth -> drift (the "two reel generators" diagnosis from Aug).
- load_state() searches content_queue, active_bundle, pending_bundle, and, since the fix,
  posted_bundle_content -> good.
- Reels accumulate in reels/ (no size/bitrate/time tracking in state.json; disk usage is not
  monitored; nothing records which bundles have published reels vs which were never generated.

### Best way forward (lightweight, no new infra)
1. Add a reel metrics record to state.json only (no new DB):
   - at publish time, record for each bundle: reel_sha256, reel_bytes, reel_duration, has_audio,
     reel_path. This is already tracked for image/story/carousel; reels is the only media missing
     this bookkeeping.
2. A 10-line `scripts/track_reel_memory.py` that reads state.json and prints per-bundle reel size
   and total disk usage of reels/, so "memory savings" can be observed (e.g., "del 5 old reels
   = 18MB back on disk").
3. Add the delete-and-regenerate loop as the documented mental model: delete reels/<old>.mp4,
   regenerate, keep only the latest. This is the intended memory-savings loop; it currently exists
   as manual CLI history, not as a script.
4. No migration needed: the pending_bundle/active_bundle/content_queue fields are now all respected
   (fixed Aug: load_state now checks all three + posted_bundle_content).

## 5. Deep Learning readiness (DEEP_LEARNING.md Phase 8)
Plan: predictive engagement/sales model trained on past posts, selecting the best candidate.
### Current dataset
- growth_data.json: 3 IG entries (2026-04 baseline, 2026-05 consolidated, 2026-06 consolidated).
- NO multi-platform, NO book-sales attribution, NO UTM/CTA metrics, NO caption/feature vectors.
- DEEP_LEARNING.md explicitly needs: reach, impressions, shares, saves, likes, comments, CTA,
  book sales, caption, hashtags, timestamps, image.
- Verdict: NOT ready to train. The required variables (book sales, CTA, multi-platform, UTM) are
  absent. The 3 IG entries are too few (<100) for a neural net.
### Recommended path (not in the file)
1. Wire growth_data.json to the 6-platform publisher (IG, Threads, LinkedIn, YouTube, Bluesky,
   Facebook) as part of the publish gate — this gives the dataset the plan assumes.
2. Add a `metrics` field to each published bundle (post IDs, reach/impressions/per-save/like/
   comment counts via the platform tokens, UTM for the CTA, book sales link).
3. Keep DEEP_LEARNING.md's 3-month rolling feature window; 2026 is the first year with enough
   posts that the rolling window now exceeds 100 rows (Apr-Jun + Oct bundles).
4. Implement the 5-step plan AFTER steps 1-2 are live: only then is the "selection engine"
   (step 4) meaningful. Do not implement neural nets before the data is complete.
### Bottom line
Ready to IMPLEMENT the data pipeline (steps 1-2) today. Ready to TRAIN (step 3) only when 12+ months
of multi-platform data exist. The notebook approach in DEEP_LEARNING.md (Pandas + Keras) is fine;
the blocker is data, not model.
